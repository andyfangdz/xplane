# Measurement method

The experiment repeats the automated TorqueSim SR20 power-off 180 at KCDW runway 22. It reproduces the earlier landing-test environment: the runner's reduced 2D graphics profile, stock scenery, calm fixed weather, full fuel, 200 lb in each front seat and temporary isolation of TelemFFB-XPP. Other global plugins remain installed. It does not reproduce the user's high-detail VR/custom-scenery environment or a long cross-country streaming workload.

One session contains two identical flights with fresh aircraft loading. The stutter comparison uses A1, B1, C1, D1, D2, C2. A = no flag/cache 5 GB; B = flag/cache 5 GB; C = flag/cache 0; D = no flag/cache 0. Thus A/B each have two flights in one process, while C/D each have four flights across two processes, including a reversed repeat. Thousands of frames are not thousands of independent experiments. B2 is used only for load timing; it is stopped deliberately after first successful resume and contributes no stutter/landing data. No A2 session is run.

Driver, scenery, rendering preferences, aircraft loading and control binaries are held constant. The installed hardware is Ryzen 9 9950X3D and GeForce RTX 5090 with NVIDIA 616.92. Temporary preference changes are applied exclusively by `Run-XPlaneTest.ps1`; each run has full, verified recovery before the next launches. The default cache was already full at approximately 5 GB. No manual cache clearing is performed, and cache contents evolve naturally. This is a capacity-toggle experiment, not a controlled cold-cache test.

The new runtime 0.8.4 observes a monotonic `std::time::Instant` at every after-physics callback entry, before telemetry reads and buffered trace writes. The callback requests the next loop every time. Native guidance and attitude gains/thresholds are unchanged. Every compared flight uses this same instrumented binary. The existing 84 columns are preserved and five are appended.

`wall_frame_dt_s` is the uncapped difference between consecutive callback timestamps, in seconds. The first active sample has no preceding measurement and is recorded as zero; pause/resume resets the prior timestamp to exclude setup pauses. Every positive interval is retained, including outliers. This measures simulator loop pacing, not monitor/VR-compositor presentation. `render_frame_period_s` is only a smoothed corroborating signal. `gpu_frame_time_s_approx` is explicitly approximate in the SDK and is not used to assign a CPU/GPU cause.

The primary comparison uses the count of wall intervals **strictly greater than 50 ms**, normalized by measured wall minutes. Secondary measures include >100 ms pauses, p99/p99.9, maximum interval, and average callback frequency. Adjacent slow intervals are also grouped as events. Percentiles use linear interpolation between ordered observations. Pauses are measured across the complete recorded maneuver, including stabilized downwind and initial rollout, without trimming unfavorable phases.

Timing integrity is checked independently against adjacent monotonic elapsed timestamps and the controller's native step sequence. The SDK global counter advances by two on this beta at each logged callback; that observed increment is retained rather than incorrectly assuming it must be one. The [SDK describes it as a dispatch counter](https://developer.x-plane.com/sdk/XPLMFlightLoop_f/), not a display frame number.

An injected `after_prepare` failure with the flag and cache 0 verified restoration before live tests. All 88 Rust tests and 15 Python tests in the existing harness passed, along with release build, PowerShell parsing and exact-process checks. Two additional analysis tests cover known pause counts/exposure and detection of a missing timing sample. Raw traces, startup failures if any, landing assessments and restoration evidence are retained separately. A setup probe is not a flight, and a passing landing alone does not prove smooth rendering.

## Loading benefits

The user's cache question concerns faster loading and streaming. Loading is measured separately using the original, contemporaneous file timestamps: `flight-request.json` is atomically saved immediately before POST `/flight`; `startup-resume.json` is saved after the first successful unpause readback. Inspection of the adapter confirms the latter occurs before repeated configuration, aircraft mass activation and fuel stabilization. Their timestamp difference therefore measures flight loading plus catalog/readiness checks, excluding the later fuel/mass setup. It is a reproducible operational readiness measure, not a GPU-present timestamp or a direct measurement of texture-decoding CPU time. The original nanosecond timestamps are embedded in `load-results.json` before copying artifacts.

The event history supplies an independent check on the request marker, and separately records the interval through initial configuration and through full flight-test setup. X-Plane launch-to-first-resume is also retained. No menu recovery was needed in the observations available at the time this method was written; final evidence must verify that across all sessions.

First loads in fresh simulator processes are kept separate from reloads in the same process. A fast same-process reload cannot be attributed specifically to the new disk texture cache: memory-resident scenery/assets and the operating system's file cache can help even when the X-Plane cache is disabled. Neither OS caches nor disk texture-cache contents are deliberately cleared. Original high-detail custom scenery, VR and long-route streaming are outside this comparison.

A separate focused capacity comparison uses 5, 10, 10, 5 GB in fresh simulator processes, with the flag enabled in all four. B2 provides the first 5 GB observation; L10a, L10b and L5b provide the remaining observations. The official cancellation command is issued after the first successful-resume marker. This intentionally returns a cancellation error and triggers normal verified recovery before airborne guidance begins. These are planned loading-only stops, with zero flight traces, and are neither failed landings nor stutter evidence. Cache 10 GB starts with the existing warm 5 GB contents and can populate further; this is a practical capacity comparison rather than an equal-content or cold-cache experiment.
